# 0004. Протокол сетевого взаимодействия нод (HTTP + JSON / REST)

* **Статус:** Принято
* **Дата:** 2026-11-12

## Контекст и постановка проблемы

В спринте 4 система переходит от одного сервера с локальным файлом блокчейна к сети из 2+ независимых нод. Ноды должны: обмениваться информацией о состоянии цепочки, передавать новые блоки друг другу, валидировать полученные блоки и отклонять некорректные с описанием ошибки. Автоматическая синхронизация в спринте не обязательна, но формулировка задачи подразумевает её появление в будущих спринтах — решение не должно требовать переделки архитектуры при переходе к ней.

Ограничения: стек проекта — Node.js/Express; команда учебная, срок — один спринт; развёртывание локальное (2–3 процесса на одной машине).

## Рассмотренные альтернативы

1. **WebSocket (постоянное двунаправленное соединение):**
   * *Плюсы:* мгновенная доставка событий без опроса; одно соединение на пару нод.
   * *Минусы:* нужно управлять жизненным циклом соединений (обрывы, переподключения, heartbeat); тестирование требует WS-клиента вместо обычных HTTP-инструментов; при редких событиях (несколько документов в минуту) постоянное соединение простаивает. Запрос блоков «по требованию» всё равно пришлось бы делать отдельно.
2. **Брокер сообщений (RabbitMQ / Redis pub-sub):**
   * *Плюсы:* буферизация сообщений для офлайн-нод, гарантированная доставка из коробки.
   * *Минусы:* отдельный сервис-посредник, который каждому члену команды нужно установить и поддерживать; новый для команды стек; избыточная инфраструктура для сети из 2–3 нод.
3. **Готовый P2P-стек (libp2p):**
   * *Плюсы:* обнаружение соседей, обход NAT, gossip-протоколы из коробки.
   * *Минусы:* тяжёлая зависимость с высокой сложностью; скрывает механику взаимодействия, которую команда как раз должна изучить и показать; неоправдан для учебного MVP в локальной сети.
4. **HTTP + JSON (REST, запрос-ответ):**
   * *Плюсы:* Express уже используется, новых зависимостей ноль (встроенный `fetch` в Node 18+); тестируется curl/Postman/Jest; явный контракт «запрос → ответ → ошибка» ложится на требование «отклонять с описанием ошибки»; естественная эволюция к автосинхронизации (планировщик поверх тех же эндпоинтов).
   * *Минусы:* нет постоянного канала — при будущей автосинхронизации задержка определяется интервалом опроса; нет встроенной гарантированной доставки (для офлайн-соседей понадобится очередь повторов); при 3+ нодах каждая должна знать всех соседей (full mesh), пока нет gossip.

## Решение

Использовать **HTTP + JSON (REST)** для всего меж-нодового взаимодействия:

- P2P API на существующем Express-сервере: `GET /api/node/info`, `GET /api/node/blocks` (диапазоном), `GET /api/node/blocks/:index`, `POST /api/node/blocks` (приём с валидацией), `POST /api/node/sync` (ручной pull). Полный контракт — `docs/architecture/sprint4-requirements.md`.
- Адреса соседей — из конфигурации (`PEERS`), без динамического обнаружения.
- Совместимость сети — по хэшу genesis-блока (`networkId`); доступ к P2P API — по общему секрету в заголовке `X-Network-Token`.
- Приём блока идемпотентен (повторная доставка того же блока не создаёт дубль) — это сознательное требование ради будущей автосинхронизации и ретраев.
- Рассылка нового блока — push после успешного commit бизнес-операции; недоставка логируется и не ломает операцию.

## Ожидаемые последствия и компромиссы

* **Положительные:**
  * Нулевые новые зависимости и инфраструктура: две ноды поднимаются двумя npm-скриптами на любой машине команды.
  * Прозрачность и тестируемость: каждый сценарий (включая негативные) воспроизводится одним curl-запросом; контракт ошибок формализован кодами.
  * Путь развития без слома API: автосинхронизация = новый модуль-планировщик поверх существующих эндпоинтов; гарантированная доставка = очередь недоставленных блоков (outbox) + ретраи; мгновенные уведомления при желании добавляются отдельным каналом (SSE/WebSocket) поверх неизменного REST.
* **Компромиссы (с чем придётся работать):**
  * Пока сосед офлайн, блок ему не доставлен — догнать можно только вручную через `/sync` (до появления планировщика и outbox).
  * Форки (расхождение цепочек) в этом спринте отклоняются (`BLOCK_CONFLICT`), правило выбора цепочки — задача на будущее.
  * Подписи блоков (Ed25519) не реализованы; защита ограничена общим токеном и проверкой genesis.
