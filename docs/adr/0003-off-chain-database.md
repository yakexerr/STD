# 0003. Выбор реляционной СУБД для Off-chain хранилища (MySQL)

* **Статус:** Принято
* **Дата:** 2026-10-07

## Контекст и постановка проблемы
В рамках утвержденной гибридной модели хранения данных (ADR-0002) блокчейн-реестр хранит только криптографические доказательства подлинности (хэши, статусы и идентификаторы). Персональные данные пользователей, роли, метаданные документов и историю запросов на верификацию необходимо вынести в надежное внешнее Off-chain хранилище.

Необходимо выбрать СУБД, обеспечивающую строгую целостность связанных сущностей (`users` <-> `documents` <-> `verification_requests`), поддержку транзакций и простоту развертывания в связке с бэкендом на Node.js.

## Рассмотренные альтернативы
1. **Документоориентированная СУБД (MongoDB):**
   * *Плюсы:* Гибкая бессхемная модель данных, нативная работа с JSON-документами в экосистеме Node.js.
   * *Минусы:* Отсутствие декларативной ссылочной целостности (Foreign Keys); повышенный риск нарушения консистентности между пользователями и документами; избыточная сложность при моделировании строгих реляционных связей учетных записей.
2. **Объектно-реляционная СУБД (PostgreSQL):**
   * *Плюсы:* Развитая поддержка стандартов SQL, строгая транзакционность (ACID), богатый функционал работы с комплексными типами данных.
   * *Минусы:* Избыточный для текущего MVP функционал; более высокие накладные расходы на локальное администрирование и разграничение прав доступа в рамках учебного спринта.
3. **Файловая встраиваемая СУБД (SQLite):**
   * *Плюсы:* Отсутствие необходимости развертывать отдельный сервер базы данных, хранение базы в одном файле.
   * *Минусы:* Блокировка всей базы данных на уровне файла при операциях записи (`WRITE`), что создает риски нестабильности при одновременных запросах от веб-клиента.
4. **Реляционная СУБД (MySQL):**
   * *Плюсы:* Надежный транзакционный движок InnoDB с полной поддержкой ACID; строгий контроль внешних ключей; нативная поддержка перечислений (`ENUM`) для ролей (`ISSUER`, `HOLDER`) и статусов документов (`VALID`, `REVOKED`); зрелая экосистема драйверов и ORM для Node.js; низкий порог входа для локального запуска команды.
   * *Минусы:* Необходимость запуска и поддержки отдельного сервиса СУБД (локально или через Docker).

## Решение
Использовать реляционную СУБД **MySQL** (движок **InnoDB**) в качестве основного Off-chain хранилища данных с базовой схемой таблиц:
* `users` (`id`, `email`, `password_hash`, `role`)
* `documents` (`id`, `type`, `issuer_id`, `holder_id`, `file_name`, `document_hash`, `status`, `issued_at`
* `verification_requests` (`id`, `user_id`, `document_hash`, `result`, `created_at`)

## Ожидаемые последствия и компромиссы
* **Положительные:**
  * Гарантированная ссылочная целостность: невозможно создать запись документа для несуществующего эмитента или выпускника благодаря внешним ключам.
  * Валидация допустимых статусов и ролей на уровне самой базы данных через тип `ENUM`.
  * Быстрая интеграция с Node.js бэкендом через стандартные ORM (Sequelize/Prisma) или библиотеку `mysql2`.
* **Компромиссы (с чем придется работать):**
  * Членам команды необходимо иметь установленный локальный экземпляр MySQL или поднимать сервис через Docker Compose.
  * Любые последующие изменения структуры таблиц потребуют механизма миграций схемы базы данных.
