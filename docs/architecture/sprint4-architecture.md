# Архитектура спринта 4 — сеть нод

## 0. Цель и границы

**Цель:** уйти от одного сервера с одним файлом блокчейна к сети из 2+ независимых нод, которые обмениваются блоками по сети.

**Нода** — запущенный экземпляр нашего существующего сервера (`server/server.js`) со своими настройками: свой порт, свой файл блокчейна, свой список соседей. Код НЕ дублируется — один репозиторий, несколько процессов.

Делаем:
- запуск ≥2 нод, у каждой своё хранилище блокчейна;
- общение по известным адресам (список соседей в конфиге);
- запрос информации о ноде и её цепочке;
- передача нового блока соседу (push) и запрос блоков у соседа (pull);
- валидация полученного блока перед добавлением, отказ с описанием ошибки.

НЕ делаем (осознанно вынесено за границы спринта):
- автосинхронизация по расписанию (только push при выпуске/отзыве + ручной pull);
- консенсус и разрешение форков (fork — расхождение цепочек у двух нод);
- gossip (пересылка полученных блоков дальше другим соседям);
- репликация MySQL и PDF-файлов между нодами;
- криптографические подписи блоков.

## 1. Схема сети

```
┌───────── Нода 1 (:5001) ─────────┐        ┌───────── Нода 2 (:5002) ─────────┐
│ Express                          │  HTTP  │ Express                          │
│  ├ бизнес-API (auth/docs/valid.) │ +JSON  │  ├ бизнес-API (auth/docs/valid.) │
│  └ P2P-API /api/node/* (новое)   │◄──────►│  └ P2P-API /api/node/* (новое)   │
│ Blockchain → data/node1.json     │        │ Blockchain → data/node2.json     │
└──────────────┬───────────────────┘        └──────────────┬───────────────────┘
               └────────────► MySQL std_db (общая) ◄───────┘
```

- **Блокчейн у каждой ноды свой** (требование ТЗ), файлы разные.
- **MySQL одна общая** (`std_db`), схема не меняется. Обоснование: ТЗ требует независимости именно хранилища блокчейна; пользователи и метаданные документов — off-chain данные, их репликация — отдельная задача будущих спринтов.
- **Формат блоков не меняется** (см. sprint2-architecture.md §3). Совместимость обеспечивается тем, что обе ноды работают на одном коде ядра.
- **Общая история:** все ноды сети обязаны иметь одинаковый genesis-блок (нулевой блок BEGIN). Хэш genesis = `networkId` (идентификатор сети). Ноды с разным genesis — разные сети,.blocks друг друга не принимают.

## 2. Протокол взаимодействия: HTTP + JSON (REST)

Запрос-ответ: нода шлёт HTTP-запрос соседy, получает JSON-ответ.

Почему:
- Express уже есть, новых зависимостей ноль (в Node 18+ есть встроенный `fetch`);
- тестируется чем угодно: curl, Postman, Jest;
- синхронный запрос-ответ точно покрывает сценарии ТЗ «запросить и получить».

Альтернативы (отклонены):
- **WebSocket** (постоянное соединение) — даёт мгновенные уведомления, но избыточен: автосинхронизация не требуется, а push у нас и так мгновенный;
- **очереди сообщений** (RabbitMQ и т.п.) — лишняя инфраструктура для 2 нод;
- **libp2p** — сложный P2P-стек, неоправдан для учебного MVP.

**Путь к автосинхронизации без переделки:** контракт сразу проектируем пригодным для неё — идемпотентный приём блока (повторная отправка того же блока не создаёт дубль), выдача блоков диапазоном, мета о длине цепочки в `/info`. В будущем добавляется модуль-планировщик (раз в N секунд опросить соседей и догнать цепочку), который вызывает те же эндпоинты. Текущий API менять не придётся.

## 3. Конфигурация и запуск

### 3.1. Новые переменные окружения (server/config.js)

| Переменная | Значение по умолчанию | Смысл |
|---|---|---|
| `NODE_ID` | `node-<PORT>` | имя ноды для логов и ответов |
| `PORT` | `5000` | порт этой ноды |
| `BLOCKCHAIN_FILE` | `blockchain/blockchain.json` | файл цепочки; путь от корня репо |
| `PEERS` | `''` | адреса соседей через запятую, напр. `http://localhost:5002` |
| `NETWORK_TOKEN` | `''` | общий секрет сети; пусто = проверка отключена |
| `P2P_TIMEOUT_MS` | `5000` | таймаут запросов к соседям |

Существующие `DB_*` не меняются — обе ноды смотрят в одну `std_db`.

### 3.2. Файлы окружения в корне репо

`.env.node1`:
```
NODE_ID=node-1
PORT=5001
BLOCKCHAIN_FILE=data/node1.json
PEERS=http://localhost:5002
NETWORK_TOKEN=std-network-secret
```
`.env.node2` — зеркально: `NODE_ID=node-2`, `PORT=5002`, `BLOCKCHAIN_FILE=data/node2.json`, `PEERS=http://localhost:5001`, тот же `NETWORK_TOKEN`.

### 3.3. Скрипты и запуск

В корневой package.json добавляются скрипты:
```json
"start:node1": "node -r dotenv/config server/server.js dotenv_config_path=.env.node1",
"start:node2": "node -r dotenv/config server/server.js dotenv_config_path=.env.node2"
```
(`-r dotenv/config ... dotenv_config_path=...` — стандартный способ dotenv загрузить конкретный .env-файл до старта скрипта.)

В репо коммитятся: `.env.node1`, `.env.node2` (корень) и `frontend/.env.development`:
```
VITE_API_URL=http://localhost:5001/api
```
Vite сам подхватывает `.env.development` при `npm run dev` — фронт по умолчанию ходит в ноду 1. Чтобы смотреть глазами ноды 2: поменять порт на 5002 и перезапустить dev-сервер.

**Разовая подготовка (один раз):**
1. MySQL запущен, `std_db` создана — как в спринте 2, ничего нового.
2. Bootstrap общей истории — §3.4 (скопировать blockchain.json в data/ ДО первого запуска нод).

**Каждый запуск — 3 терминала:**

| Терминал | Рабочая папка | Команда | Что запущено |
|---|---|---|---|
| 1 | корень репо | `npm run start:node1` | нода 1 → http://localhost:5001, файл data/node1.json |
| 2 | корень репо | `npm run start:node2` | нода 2 → http://localhost:5002, файл data/node2.json |
| 3 | frontend/ | `npm run dev` | фронт → http://localhost:5173, API ноды 1 |

Признак успеха: в логах нод `Server is running on port 5001/5002`. Быстрая проверка: открыть в браузере http://localhost:5001/api/node/info → ответ `401 UNAUTHORIZED` означает, что нода жива (браузер не шлёт токен; полный ответ — curl с токеном, requirements §7).

**Совместимость:** обычный `npm start` (одна нода на :5000) работает как в спринте 3; для него во фронте убрать `VITE_API_URL` или указать порт 5000.

### 3.4. Bootstrap (начальная общая история) — ВАЖНО

Файл блокчейна копируем в data/ **до первого запуска** обеих нод:
```
mkdir data
copy blockchain\blockchain.json data\node1.json
copy blockchain\blockchain.json data\node2.json
```
(на Linux/macOS — `cp`). Если этого не сделать, каждая нода при первом старте создаст СВОЙ genesis → получатся две разные сети, и блоки не будут приниматься.

### 3.5. Правки существующего кода

- `server/server.js`: `new Blockchain(path.join(__dirname, '..', config.BLOCKCHAIN_FILE))` — путь якорится от корня репо, а не от текущей рабочей директории (запуск из `server/` тоже работает); подключить роутер `/api/node`.
- `frontend/src/services/api.js`: `baseURL = import.meta.env.VITE_API_URL || 'http://localhost:5000/api'`. Для демо с нодой 1 запускаем фронт с `VITE_API_URL=http://localhost:5001/api`.

## 4. Изменения в ядре (blockchain/blockchain.js)

1. **Вернуть проверку целостности в `load()`** — сейчас `throw` закомментирован. Повреждённая цепочка должна падать при старте, а не работать молча.
2. **`issueDocument`/`revokeDocument` перед добавлением блока вызывают `validateChain()`**; при повреждении — ошибка с `code = 'BLOCKCHAIN_TAMPERED'` (как в `checkDocument`).
3. **Новый метод `getBlocks(fromIndex = 0, limit = 100)`** → массив блоков (обычные JSON-объекты через `toJSON()`), срез цепочки. Ничего не меняет.
4. **Новый метод `addExternalBlock(blockData)`** — единственный путь добавить блок, полученный из сети. Порядок проверок (каждый шаг при провале даёт свою ошибку с `code` и `details`, полный контракт — в sprint4-requirements.md §3.4):
   1. целостность собственной цепочки (`validateChain`);
   2. формат верхнего уровня: 6 полей, типы, index — целое ≥ 0, хэши — 64 hex;
   3. тип блока: только `ISSUE` или `REVOKE` (`BEGIN` из сети не принимается);
   4. схема `data` соответствует типу (ISSUE: 4 непустых строковых поля, documentHash — 64 hex; REVOKE: documentId);
   5. пересчёт хэша: `calculateHash()` от полученных полей === `block.hash`;
   6. дубликат: блок с таким index и таким же hash уже есть → `{ accepted: false, reason: 'DUPLICATE_BLOCK' }` (не ошибка);
   7. конфликт: на этом index у нас ДРУГОЙ хэш → отказ (форки в этом спринте не решаем);
   8. стыковка: `index === latest.index + 1` и `previousHash === latest.hash`;
   9. бизнес-правила: для ISSUE — documentId/documentHash уникальны; для REVOKE — документ существует и не отозван;
   10. добавить в цепочку + `save()`, вернуть `{ accepted: true, chainLength }`.

   Свой блок не пересчитываем: timestamp и hash берём как пришли. Полученный `data` сохраняем как есть (сортировка ключей — только внутри вычисления хэша).

## 5. P2P API (новый роутер server/routes/node.js)

Все `/api/node/*` требуют заголовок `X-Network-Token` (middleware сверяет с `config.NETWORK_TOKEN`).

| Метод и путь | Назначение |
|---|---|
| `GET /api/node/info` | кто я: id, networkId, длина цепочки, последний блок, соседи |
| `GET /api/node/blocks?fromIndex=&limit=` | отдать блоки диапазоном (для pull) |
| `GET /api/node/blocks/:index` | отдать один блок |
| `POST /api/node/blocks` | принять блок от соседа (валидация → добавить/отказать) |
| `POST /api/node/sync` | ручной pull: догнать цепочку с соседа/соседей |

Логика выносится в `server/services/p2pService.js` (HTTP-клиент к соседям + рассылка). Полные форматы запросов/ответов/ошибок — **sprint4-requirements.md**.

## 6. Сценарии

### 6.1. Push — выпуск документа рассылается соседям
```
ISSUER → Нода1: POST /api/documents/issue (PDF, как в спринте 2)
Нода1: блок ISSUE в data/node1.json + запись в MySQL, commit
Нода1 → Нода2: POST /api/node/blocks { block }   (после commit!)
Нода2: валидация по §4.4 → 201 { accepted: true }
Проверка того же PDF через Нода2 → VALID
```
Правила рассылки:
- отправка ПОСЛЕ успешного commit в БД;
- соседи берутся из `PEERS`, отправка параллельная, таймаут `P2P_TIMEOUT_MS`;
- сосед недоступен/отказал → пишем в лог, **выпуск документа НЕ падает** (ответ бизнес-API не меняется);
- повторов нет, полученных блоков дальше не пересылаем (нет gossip). При 3+ нодах каждая должна знать всех остальных (список PEERS полный).

### 6.2. Pull — ручная синхронизация
```
(Нода2 была выключена, на Ноде1 выпустили документы)
Кто-то → Нода2: POST /api/node/sync {}
Нода2 → каждый сосед: GET /api/node/info
  networkId не совпал → пропустить соседа с ошибкой GENESIS_MISMATCH
  сосед длиннее → GET /api/node/blocks?fromIndex=<моя длина>&limit=100
  применять блоки по одному через addExternalBlock, до первого отказа
Нода2: 200 { results: [...по каждому соседу...], chainLength }
```

### 6.3. Негатив — сосед прислал плохой блок
```
НодаX → Нода2: POST /api/node/blocks { block с испорченным hash }
Нода2: шаг 5 провален → 422 { error: { code: 'INVALID_HASH', message, details: { expected, received } } }
Цепочка Ноды2 не изменилась.
```

## 7. Безопасность (минимум для учебного спринта)

- **`X-Network-Token`** — общий секрет в заголовке, чтобы посторонние не слали блоки. Не совпал → 401.
- **`networkId` (хэш genesis)** — проверка «мы из одной сети» при sync; при push несовместимость выявится отказом на шагах 7-8 валидации.
- Подписи блоков (Ed25519 из «Описание формата.md») — future work.

## 8. Ограничения и эволюция

| Ограничение сейчас | Как снимается потом (без смены протокола) |
|---|---|
| синхронизация только push + ручной pull | модуль-планировщик поверх тех же эндпоинтов |
| нет повторов при недоступном соседе | очередь недоставленных блоков (outbox) + ретраи |
| форки отклоняются (BLOCK_CONFLICT) | правило «длиннейшая валидная цепочка» в ядре |
| нет gossip | пересылка принятых блоков дальше / планировщик |
| MySQL и PDF не реплицируются | отдельный спринт по off-chain репликации |

## 9. Критерии приёмки

- [ ] `npm run start:node1` и `npm run start:node2` поднимают две ноды, у каждой свой файл в `data/`;
- [ ] `GET /api/node/info` на обеих отвечает, `networkId` совпадает;
- [ ] выпуск диплома на Ноде1 → блок появляется в `data/node2.json` без ручных действий;
- [ ] тот же PDF проходит проверку на Ноде2 → `VALID`; отзыв на Ноде1 → на Ноде2 `REVOKED`;
- [ ] выключенная нода после `POST /api/node/sync` догоняет цепочку;
- [ ] битый блок (хэш/previousHash/index/дубликат документа) отклоняется с JSON-ошибкой `code + details`, цепочка не меняется;
- [ ] повторная отправка того же блока → `200 accepted:false`, дубль не создаётся;
- [ ] сосед офлайн → выпуск документа всё равно успешен, в логе ошибка доставки;
- [ ] существующие тесты зелёные, новые тесты по sprint4-test-scenarios.md проходят.
