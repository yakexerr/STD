# Правила разработки (Workflow)

## 1. Работа с ветками
- Ветка `main` — только для стабильного кода. Пушить напрямую в `main` **ЗАПРЕЩЕНО**.
- Для каждой задачи создается отдельная ветка с понятным префиксом:
    - `feature/имя-задачи` - для новой функциональности;
    - `fix/имя-бага` - для исправления ошибок;
    - `docs/название-документа` - для документации и архитектурных описаний.

## 2. Процесс разработки (Git Flow)
1. Разработчик берет задачу из колонки **Ready**, переносит в **In Progress** и назначает себя исполнителем.
2. Создает тематическую ветку от актуального main.
3. Реализует задачу, пишет тесты и проверяет код линтером.
4. Создает **Pull Request** (PR) из своей ветки в `main`.
5. В PR назначает Тестировщика (Reviewer).

## 3. Тестирование и Review
1. Тестировщик переносит задачу в колонку **In review**.
2. Проводит **Code Review** и **Функциональное тестирование** (черный ящик) по ТЗ.
3. Если всё ок — ставит `Approve` и вливает PR в `main`.
4. Если есть ошибки — оставляет комментарии и возвращает на доработку.

## 4. Критерии готовности задач (Definition of Done)
Задача считается полностью завершенной (**Done**), если:
- Код написан в отдельной ветке и успешно проходит проверку линтером (ESLint) без предупреждений и ошибок.
- Оформлен Pull Request с описанием изменений.
- Получен как минимум один `Approve` от участника команды.
- Ветка успешно смержена в `main`.
- Связанная документация (README, ADR, схемы) обновлена при необходимости.

## 5. Стиль кода
1. Используем стандарт: **JavaScript Standard Style** с проверкой через **ESLint**.
2. Комментарии к методам обязательны (формат не регулируется).

3. Логическое разбиение (Секции)
Длинные файлы должны быть разбиты на логические блоки с помощью визуальных комментариев-заголовков. Это помогает быстро ориентироваться в структуре файла.

    3.1 **Пример для CSS:**
    ``` css
    /* NAVIGATION */

    .nav-item { ... }

    /* FOOTER */

    .footer { ... }
    ```

    3.2 Пример для js:

    ``` JavaScript
    // ОБРАБОТЧИКИ СОБЫТИЙ (EVENT HANDLERS) 

    function handleClick() { ... }
    ```

4. TODO подписывать собственным ником или именем:
    ```js
    //TODO(nickname) ...
    ```

## 6. Правила именования коммитов
При комментировании используем стандарт **Conventional Commits**. Каждый коммит должен начинаться с типа и краткого описания в формате: `тип(область): описание`.

| Тип | Когда использовать |
| :--- | :--- |
| **feat** | **Feature** — новая функциональность (например: добавил возможность выбора проекта). |
| **fix** | **Fix** — исправление ошибки (например: починил SqliteError, поправил CSS). |
| **docs** | **Docs** — изменение документации (README, ADR, C4). |
| **style** | **Style** — форматирование, отступы (не меняет логику работы, просто чтобы красиво). |
| **refactor** | **Refactor** — изменение кода без добавления функций или исправления багов. |
| **perf** | **Performance** — улучшение производительности (например: ускорил SQL-запрос). |
| **test** | **Test** — добавление или изменение тестов. |

---
**Примеры:**
* `feat(db): add sprint tables and foreign keys`
* `fix(tasks): resolve duplicate task issue in kanban`
* `style(ui): fix navigation bar layout`
